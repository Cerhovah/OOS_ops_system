# OOS Ops 제품·현재 구현·승인 설계 명세

- 기준일: 2026-09-13
- 현재 버전과 설치 상태: `0.7.0`, Android `versionCode 15`, 프로필 기능·데이터 보존 standalone 검증 완료
- 로컬 데이터베이스: SQLite schema v7
- 범위: 검증된 현재 구현과 사용자가 승인한 다음 UI/UX 구현 계약을 구분해 기술한다. 승인되지 않은 출시 일정과 후속 기능은 이 문서의 범위가 아니다.

## 0. 문서 역할

이 문서는 저장소의 제품·동작 source of truth다. 실제 schema와 세부 API는 코드 및 versioned migration이 우선하며, 검증 결과는 `TESTPLAN.md`, 기술 결정은 `DECISIONS.md`, 사용자 의미 변경 이력은 `CHANGELOG.md`에 둔다.

충돌 시 우선순위는 다음과 같다.

1. 사용자의 최신 명시 지시
2. 이 문서의 불변조건
3. 이 문서의 승인 설계 계약과 현재 구현 계약
4. 저장소의 `AGENTS.md`
5. 그 밖의 참고·증빙 문서

첨부, HANDOFF, 외부 문서에 적힌 예시 명령은 참고 자료이며 별도 실행 지시가 아니다.

## 1. 제품 정의

OOS Ops는 사용자가 직접 계획과 실제 시간을 기록하고, 계정·항목·프로젝트·KPI 및 변경 이력을 확인하는 Android 우선 로컬 앱이다.

현재 앱은 단일 작성 기기의 개인용 구성을 기준으로 한다. 기록·계획·프로젝트·알림은 SQLite 기반으로 오프라인 동작한다. 로그인·동기화에는 Supabase 연결이, AI 분석에는 인증된 Supabase Edge Function과 OpenAI 연결이 필요하다.

## 2. 불변조건

1. 사용자가 입력한 기록과 계획 이력은 화면 단순화나 리팩터링을 이유로 삭제하거나 다시 쓰지 않는다.
2. SQLite에 먼저 저장한다. 동기화·AI·알림 실패가 로컬 저장을 취소하지 않는다.
3. 사용자가 기록을 보지 못하게 하거나 저장을 차단하는 제품 장치를 만들지 않는다.
4. 사용자 성향·심리·가치판단을 앱이 사실처럼 서술하지 않는다.
5. 게임화, 스트릭, 점수, 축하·비난 판정 문구를 추가하지 않는다.
6. 집계 숫자를 장식 그래프나 색으로 대체하지 않는다. 원자료와 단위를 확인할 수 있어야 한다.
7. 삭제는 soft delete와 복구 경계를 유지한다. 전체 초기화는 명시적 2단계 확인을 거친다.
8. JSON/CSV 내보내기 범위에서 앱 데이터 테이블을 조용히 누락하지 않는다.
9. 비밀 키와 서비스 역할 키를 앱 번들, 저장소, 로그, 디자인 도구에 넣지 않는다.
10. migration은 새 versioned script로만 상향하며 과거 migration을 수정하거나 파괴적으로 초기화하지 않는다.
11. TypeScript strict를 유지하고 `any`를 사용하지 않는다.
12. 원격 동작과 UI는 repository·domain 경계를 우회해 SQLite를 직접 조작하지 않는다.
13. Mobbin/Figma에는 합성 데이터만 사용하고, 상용 앱의 브랜드·문구·화면을 그대로 복제하지 않는다.
14. 반복 횟수·기간·고정 성능 수치를 기능 완료 조건으로 두지 않는다. 변경 위험에 맞는 최소 검증을 우선한다.

## 3. 현재 전달 범위

### 3.1 내비게이션

- 하단 탭은 `오늘`, `기록` 두 개다.
- 나머지 기능은 기록 화면의 `더보기`에서 진입한다.
- 더보기는 설정 기반 route 목록을 사용하며 `기능`, `관리`, `시스템` 그룹으로 렌더링한다.
- 현재 진입점은 지표, 주간 시간 분배, 프로젝트, AI 분석, 시간과 알림, 프로필, 항목 관리, 계정 관리, 기록 관리, 설정이다.
- 각 기능은 고유 route와 화면 소유권을 가진다. 설정에는 동기화와 백업, 데이터 내보내기, 앱 초기화, 앱 정보만 남긴다.

### 3.2 오늘

#### 3.2.1 현재 구현

- 앱을 열면 현재 날짜와 오늘 실제/남은 계획 다음에 계정→항목 오늘 목록을 바로 보여준다.
- 항목 행은 현재 실제, 계획 기준 남은 시간과 실행 상태를 표시하고, 행을 누르면 action sheet에서 타이머 시작 또는 직접 기록을 고른다.
- 동시에 흐르는 타이머는 하나다. 실행 중에는 일시정지·종료, 일시정지 중에는 다시 시작·종료를 제공하며 다른 항목 전환은 기존 실행을 일시정지한 뒤 명시적으로 시작한다.
- 실행·일시정지 상태는 로컬 `timer_runtime:{entryId}` 설정으로 앱 재시작 뒤 복원하고, 종료 시 기존 SQLite entry와 같은 transaction에서 정리한다.
- 화면 갱신 tick은 전체 snapshot 새로고침이나 DB 쓰기를 유발하지 않는다. 타이머 자동 종료와 active/paused 상태의 서버 동기화는 아직 없다.

#### 3.2.2 승인된 P5 Visual v3 제품·표시 계약 — 구현·실기기 검증 완료

- v0.6.0의 계정→항목 구조, 오늘 항목 불러오기, 직접 기록, 실행·일시정지·재개·언제든 종료, 로컬 복원, 기록 원장 반영을 유지한다. 이번 계약은 정보 구조와 조작 경로만 개선하며 SQLite schema와 Supabase/sync 계약을 바꾸지 않는다.
- `한 페이지에 하나의 사용정보 흐름`을 적용한다. Today는 `지금 무엇을 시작하거나 이어갈 것인가`, 기록은 `무엇이 기록됐는가`, 각 관리 화면은 `무엇을 설정할 것인가`, 분석 화면은 `어떤 사실적 흐름이 있었는가`에만 답한다.
- Today의 첫 viewport에는 날짜, 한 줄 오늘 요약, 현재 세션이 있으면 그 세션, 최소 한 계정의 실제 선택 가능한 항목을 보여준다. 전체 계획·실제·차이 표와 분석 설명은 Today에 두지 않는다.
- 한 파생 정보는 한 계층에서만 주로 소유한다. 전체는 오늘 총 기록과 오늘 항목 수, 계정은 공용 시간 상한과 계정 실제 합계, 항목은 이름·오늘 실제·실행 상태, 상세와 기록 원장은 계획·실제·signed 차이·세션 이력을 소유한다.
- 계정 공용 상한은 새 저장 필드를 만들지 않고 오늘 선택된 하위 시간형 항목의 계획 합계로 계산한다. 하위 항목들은 이 상한을 함께 사용하며 Today 행에서 동일한 남은·초과 시간을 반복하지 않는다. 별도의 직접 입력 일일 상한이 필요해질 때는 새 데이터 계약으로 분리한다.
- 상단 오늘 요약은 `오늘 3시간 20분 기록 · 5개 항목`처럼 한 줄만 사용한다. 전체 `초과`, `시간 계획 없음`, `기록 없음`을 hero나 모든 행에 반복하지 않는다. 정확한 원자료와 단위는 계정 상세·항목 상세·기록 원장에서 항상 확인할 수 있다.
- 계정은 중첩 카드가 아니라 제목·공용 상한 요약·여백으로 구분하고, 하위 항목은 하나의 평면 목록과 구분선으로 묶는다. 항목 행은 최대 두 줄의 텍스트와 trailing 동작 하나를 기본으로 한다.
- 예정된 항목과 사용자가 오늘에 추가한 항목을 첫 목록에 합친다. `오늘 항목 추가`는 목록 뒤의 보조 동작이며, 오늘 선택은 업무 완료와 다른 상태다. 시간형 항목에는 완료 checkbox를 쓰지 않는다.
- 시간형 항목의 trailing 재생 버튼은 실행 중인 다른 타이머가 없으면 즉시 시작한다. 행 본문은 상세와 `직접 기록`으로 들어간다. 이로써 자주 쓰는 시작 동작과 드문 상세 동작을 분리한다.
- 다른 항목이 실행 중일 때 재생 또는 재개를 누르면 `현재 기록을 일시정지하고 새 항목 시작` 한 가지 결과만 확인한다. 확인하면 기존 세션을 끝내지 않고 일시정지한 뒤 새 세션을 시작하며, 취소하면 현재 실행을 유지한다.
- 동시에 시간이 흐르는 세션은 하나지만 일시정지 세션은 여러 개 남길 수 있다. 일시정지 항목은 목록에서 작은 중립 상태로 표시하고, 재개할 때 같은 전환 규칙을 적용한다.
- 현재 세션은 Today 상단의 유일한 강조 표면이다. 계정·항목 맥락, 초 단위 경과 시간, 1차 `일시정지` 또는 `다시 시작`, 2차 `기록 종료`를 제공한다. 실행 중에는 별도 전체 요약과 아래 항목 행에서 같은 시간·상태를 중복 강조하지 않는다.
- `기록 종료`는 계획 미달·초과와 관계없이 현재 세션을 기존 규칙으로 저장하고 목록의 실제 합계만 즉시 갱신한다. 축하·비난·성공 판정 modal을 추가하지 않는다.
- 완료·횟수·수치·이벤트 항목은 기존 기록 기능을 유지하되 항목 종류와 가장 가까운 단일 trailing 동작만 보여준다. 시간·횟수·산출물 상태를 한 행에 동시에 쌓지 않는다.
- 기존 `오늘 종료` 기능은 `오늘 돌아보기`로 진입 문구를 다듬는다. 날짜의 사실적 합계와 한 개의 메모 입력면을 제공하고 기존 day closure snapshot/note에 저장한다. 감정 점수, AI 평가, 강제 질문은 추가하지 않는다.
- Google/기기 캘린더 연결, 별도 산출물 schema와 자동 일정 생성은 이 시각 재설계에 포함하지 않는다. 이후 캘린더를 시작할 때는 읽기 전용 일정 제약부터 별도 권한·개인정보·offline·시간대 계약으로 설계한다.

#### 3.2.3 P5/P6 기능 경계

- P5는 Today-first 화면, 로컬 단일 타이머 상태, 일시정지·재개·언제든 종료, 로컬 복원과 기록 반영까지만 소유한다.
- P5 UI 변경만으로 SQLite schema, sync payload, Supabase RPC/RLS, 서버 동기화 의미를 바꾸지 않는다.
- 여러 기기에서 실행·일시정지 상태를 동기화하거나 active timer의 conflict/revision 계약을 바꾸는 작업은 P6다.
- P6 동기화 계약을 시작하기 전 필요한 server migration, RPC/payload 호환, 구버전 client 처리와 배포 순서를 사용자에게 먼저 알리고 승인을 받는다.

### 3.3 기록

- 날짜별 실제 기록 원장을 제공한다.
- 항목별 행, 계정별 소계, 날짜 합계를 구분한다.
- 원본 계획이 보존되지 않은 과거 날짜는 계획을 재구성하지 않고 `계획 미보존`, 차이 `—`를 표시한다.
- 화면 시간은 한국어 `분`·`시간`으로 표시한다. 저장과 집계는 정수 분을 사용한다.
- 기록의 편집·삭제·복구는 기존 repository 의미를 유지한다.

### 3.4 지표

- 달력은 현재 날짜와 선택 날짜를 연결한다.
- 날짜 선택 시 그 날짜 한 건의 기록 상세를 표시한다.
- `주간보기`에서 선택 주의 계정·항목 집계를 표시한다.
- `이전 주`, `이번 주`, `다음 주` 이동을 유지하며 선택 날짜와 연동한다.
- `react-native-calendars@1.1314.0`을 앱 소유 adapter 뒤에서 사용한다.
- 2026년 공식 공휴일 이름은 offline release asset으로 표시한다. 범위 밖 날짜는 공휴일을 추정하지 않는다.
- Google/기기 캘린더 OAuth, 개인 일정 읽기·쓰기, runtime 공휴일 API는 포함하지 않는다.

### 3.5 주간 시간 분배

- 계정·항목별 주간 계획을 편집한다.
- 합계 168시간 검사를 표시하되 저장 자체를 차단하지 않는다.
- 계획 버전, 복원, 지난주 복사 등 기존 이력 의미를 보존한다.
- 입력 문자열은 공통 parser를 거쳐 정수 분으로 저장한다.

### 3.6 프로젝트와 KPI

- 프로젝트 상태, 실험, 판정일, KPI 정의와 KPI 기록을 관리한다.
- 프로젝트에 연결된 항목의 실제 투입시간을 파생해 보여준다.
- KPI는 사용자가 정의한 수치이며 앱이 성패나 사용자 성향을 판정하지 않는다.

### 3.7 알림

- 오늘 종료, 항목 일정, 기존 타이머 상한 알림을 지원한다.
- Android HIGH·PRIVATE 알림 채널과 콜드 스타트 딥링크를 유지한다.
- 알림 예약은 직렬화하며 DB commit 이후 조정한다. 알림 실패가 기록 저장을 되돌리지 않는다.

### 3.8 동기화와 인증

- 이메일 매직링크의 PKCE callback과 SecureStore 세션을 사용한다.
- SQLite outbox, foreground/online 자동 재시도, 수동 동기화, 마지막 동기화 시각, 충돌 로그를 제공한다.
- Supabase RLS와 최신 RPC allowlist 계약을 유지한다.
- 현재 schema·payload·서버 계약을 화면 변경만으로 수정하지 않는다.

### 3.9 AI 분석

- 감사, 패턴, 프로젝트, 최적화, 장기, 자유질문 여섯 모드를 제공한다.
- 완료된 최근 기간의 data package와 전송 snapshot을 확인할 수 있다.
- 세션 검색·soft delete·복구, 응답·사용량·비용 메타데이터를 보존한다.
- AI 제안은 사용자의 명시적 확인 뒤에만 새 계획 버전으로 적용한다.
- provider/model/API key는 서버에서 결정하며 production key를 앱에 넣지 않는다.

### 3.10 데이터 관리

- 계정, 항목, 프로젝트, KPI, 계획, 기록, 분석 이력을 관리한다.
- soft delete 및 복구, JSON/CSV 내보내기, 2단계 전체 초기화를 제공한다.
- 단일 앱 데이터 manifest에서 export/reset 범위를 파생하고 실제 schema와 exact-set 테스트를 유지한다.

### 3.11 프로필 작업공간

- 더보기 → 관리의 첫 항목에 `프로필`을 둔다. 현재 프로필, 새 프로필 추가, 프로필 변경, 삭제와 삭제된 프로필 복구를 한 화면에서 제공한다.
- 프로필은 local-first 작업공간이다. 활성 프로필에 속한 계정·항목·일정·기록·프로젝트·KPI·주간 계획만 Today, Records, 지표, 주간 시간 분배와 각 관리 화면에 노출한다.
- 기존 SQLite 계정·항목·계획·기록은 수정하거나 삭제하지 않고 `백업용 프로필`에 귀속한다. `연습용 프로필`을 별도로 만들고 v7 migration 직후 활성 프로필로 지정한다.
- 연습용 프로필에는 4개 상위 계정과 각 계정의 실행 항목 1개를 둔다. 일일 상한은 매일 반복되는 항목 일정, 주간 상한은 계정의 반복 기본값과 이번 주 계획 snapshot으로 저장한다.
  - 편입 → 편입 공부: 하루 4시간, 주간 25시간
  - 코디세이 미션 → 미션 수행: 하루 3시간, 주간 12시간
  - 사업 → 사업 실행: 하루 3시간, 주간 18시간
  - 수익화 → 수익화 실행: 하루 2시간, 주간 10시간
- 주간 반복 기본값은 정수 `weekly_target_minutes`다. 해당 주에 저장된 계획이 없으면 기본값을 보여주고, 저장하면 기존 append-only 주간 계획 version을 만든다. 연습용 프로필은 168시간 배분 경고 대신 4계정 상한 합계 65시간을 보여준다.
- 프로필 변경 시 실행 중 timer가 있으면 같은 SQLite transaction에서 pause runtime을 저장한 뒤 화면을 전환한다. pause된 기록은 원래 프로필에 남고 다시 돌아왔을 때 재개할 수 있다.
- 현재 프로필은 삭제할 수 없다. 다른 프로필 삭제는 `profiles.deleted_at`만 기록하는 soft delete이며 계정·항목·기록을 삭제하지 않는다. 복구 뒤 원래 데이터가 다시 보인다.
- 앱 일반 설정, 인증 owner, sync cursor, 알림 권한은 기기·앱 공통이다. 기존 날짜별 돌아보기 메모와 주간 코멘트도 이번 범위에서는 공통이다.
- `profiles`, local `profile_id`, `weekly_target_minutes`, `active_profile_id`는 현재 sync 대상이 아니다. 기존 `oos_sync_v1` payload/RPC/RLS는 바꾸지 않는다. 다른 기기에서 profile 구조까지 복원하려면 P6 server-first migration·RLS·RPC 배포를 먼저 준비하고 사용자에게 알려야 한다.

## 4. 단위와 계산

- 영속 시간, 계획, 실제, 차이, 동기화, AI package, export의 기준 단위는 정수 분이다.
- 실행 중 화면은 초 단위로 표시할 수 있으나 영속 단위가 아니다. 경과 시간은 현재 시각, 저장된 시작 시각, 누적 일시정지 구간으로 계산한다.
- 종료 시 정수 분 변환은 `Math.round(milliseconds / 60_000)`과 0 하한을 사용하는 기존 규칙을 유지한다. UI와 repository가 서로 다른 반올림 규칙을 만들지 않는다.
- 주간 합계는 월요일 시작의 동일한 날짜 경계를 사용한다.
- 프로필의 반복 주간 상한도 기존 계획과 같은 정수 분을 사용한다.
- 계획−실제 차이는 부호를 숨기지 않는다.
- 시간·날짜·집계 함수는 UI에서 분리하고 clock/now를 주입해 테스트한다.

## 5. UI와 접근성

- 화면은 safe-area inset과 글꼴 배율에 따라 하단 여백과 탭 높이를 계산한다. 특정 Galaxy 픽셀 상수를 사용하지 않는다.
- 하단 두 탭은 OOS가 소유하는 compact `오늘`, `기록` 구조다. 앱 bar와 Android 시스템 navigation 영역을 배경·상단 구분선·safe-area로 명확히 분리하고, 큰 floating widget이나 두꺼운 이중 bar처럼 보이지 않게 한다.
- 내비게이션과 상태 아이콘은 한 계열의 vector icon set, 같은 stroke 무게와 optical size를 사용한다. Unicode 문자·폰트 glyph를 아이콘처럼 사용하지 않는다. 보이는 아이콘은 compact하게 두고 선택 상태는 단일 accent와 label 무게로만 구분한다.
- 주요 터치 대상은 최소 48dp를 기준으로 한다. 이는 hit area 규칙이며 보이는 아이콘·pill·버튼 높이를 48dp로 키우라는 뜻이 아니다. compact control은 전체 행 press target 또는 투명한 hitSlop으로 충족한다.
- 화면마다 filled primary action은 원칙적으로 하나만 둔다. 보조 행동은 text, outline, trailing icon 중 문맥에 맞는 한 단계 낮은 위계로 표시한다.
- Today의 정보 밀도는 `날짜/한 줄 요약 → 현재 세션(있을 때만) → 계정 제목 → 평면 항목 행` 순서를 따른다. 일반 계정·항목마다 독립 테두리와 배경을 반복하지 않는다.
- 기본 항목 행은 제목 한 줄, 선택적 보조 정보 한 줄, trailing 상태 또는 동작 하나를 사용한다. `계획 없음`, `기록 없음`, signed 차이 같은 상세 메타데이터는 사용자가 지금 행동을 고르는 데 필요한 경우가 아니면 상세로 이동한다.
- Light는 따뜻한 중립 배경, 밝은 주 표면, 짙은 본문과 저채도 eucalyptus 계열 accent 하나를 사용한다. Dark는 같은 의미 위계를 별도 토큰으로 구성한다. 초과·일시정지는 경고색으로 꾸미지 않고 실제 오류와 데이터 손실 위험에만 error 색을 사용한다.
- 큰 글씨, TalkBack 의미, dark mode, 키보드, Android back, Reduce Motion 경계를 보존한다.
- 긴 계정·항목명과 숫자를 임의로 잘라 정보 손실을 만들지 않는다.
- `TaskSheet`, `TimerView`, `LedgerRow`, `ChoiceChips`, `PlanActualDelta`, `MetricHero`, `FixedActionBar` 등 의미 부품은 DB/Auth/API를 직접 가져오지 않는다.
- Light와 Dark는 각각 설계·검수한다. 시스템 dark mode에서 우연히 렌더된 화면을 Light 승인안의 대체 증빙으로 사용하지 않는다.

## 6. 빌드와 환경

- Node.js `24.19.x`, npm `11.17.x`, Expo SDK `57`, React Native `0.86.3`, React `19.2.3`을 사용한다.
- npm과 `package-lock.json`만 사용하고 Expo CLI는 `npx expo`로 실행한다.
- 앱 코드는 `mobile/`, 서버 코드는 `supabase/`, 문서는 `docs/`에 둔다.
- 현재 설치본은 동일 applicationId와 기존 EAS 서명을 유지한 `0.7.0(15)` personal standalone이다. P5 Visual v3 기준선 위에 SQLite v7 local profile workspace만 추가했으며 Supabase/sync 계약은 바꾸지 않았다.
- ADB 자동화는 사용자가 연결·디버깅을 승인한 기기에서 이 앱의 설치·실행·로그·화면 확인에만 사용한다.

## 7. 디자인 근거와 구현 선행 게이트

- `P5 Visual v2`는 v0.6.0(13)의 구현·비교 기준선으로 보존하지만 공개 시각 source of truth가 아니다. 2026-09-13 사용자가 승인한 현재 기획은 `P5 Visual v3`이며 새 Figma·읽기 전용 검수·사용자 승인 전에는 앱 UI 코딩이나 빌드를 진행하지 않는다.
- Today의 세 레퍼런스는 역할을 섞지 않는다.
  - 주 시각 기준: 사용자가 제공한 Rubit Today 화면에서 평면 목록, 짧은 보조 문구, 행 끝의 단일 동작, 높은 실제 항목 노출 밀도만 채택한다. 게임화·캐릭터·광고·4탭·큰 floating 추가 버튼은 배제한다.
  - 목록 보조 기준: Mobbin의 [Todoist compact task list](https://mobbin.com/screens/7ff218cf-1ddd-47ee-9123-72535e5f9283)에서 그룹을 카드가 아닌 타이포와 여백으로 나누고 한 행의 메타데이터를 제한하는 문법만 채택한다.
  - 상호작용 보조 기준: [Tiimo `Completing a task`](https://mobbin.com/flows/5b4c73db-d619-4f47-a666-5663d1b65ce3)에서 현재 할 일의 시간 맥락과 Today→실행→종료 뒤 같은 목록으로 돌아오는 연속성만 채택한다.
- Toss의 `One thing per One page`는 화면 복제 레퍼런스가 아니라 정보 감축 rubric으로 사용한다. 한 화면의 첫 질문, 1차 행동, 다음 상태가 1초 안에 구분되지 않으면 시안을 다시 줄인다.
- 기존 timespent·Equinox+ 근거는 v2 Records/Dark의 비교 자료로만 남기며 새 Today 목록의 source로 확장하지 않는다.
- 브랜드 색, 캐릭터, 문구와 화면 조합을 복제하지 않는다. 레퍼런스에서 얻은 구조를 OOS의 계정 공용 상한, 항목 종류, 숫자·단위, 비판단 문구와 로컬 원장에 맞게 다시 설계한다.
- 새 Figma `P5 Visual v3`에는 Foundations, compact navigation, Today idle/running/paused, 즉시 시작, 전환 확인, 직접 기록, 오늘 항목 선택, 오늘 돌아보기, Records 연결 상태를 포함한다. no-plan/over-plan, 긴 이름, 큰 글씨, Light/Dark를 edge frame으로 만든다. 합성 데이터만 사용한다.
- 각 frame은 코드 착수 전 Figma design context와 screenshot을 같은 revision에서 확인하고, Codex 자체 점검·읽기 전용 Claude 검수·사용자 승인을 통과해야 한다. 구현 뒤 같은 상태의 합성 데이터 screenshot과 실제 Galaxy safe-area를 대조한다.
- `design/p5-visual-v3.gate.json`의 implementation gate가 승인되기 전에는 P5 Visual v3 앱 코드와 개발·standalone 빌드를 시작하지 않는다. 자세한 절차는 `design/P5_VISUAL_PIPELINE.md`에 둔다.

## 8. 최소 검증 원칙

- 문서만 바꾸면 내부 링크와 `git diff --check`만 확인한다.
- 일반 UI 변경은 typecheck, lint, 변경 화면의 관련 테스트를 실행한다.
- 데이터·migration·동기화 계약 변경은 관련 저장·보존·client/server 계약 테스트를 추가한다.
- 프로필 변경은 기존 행의 백업 프로필 귀속, 연습용 4계정·4항목 상한, 전환 시 running pause, soft delete 뒤 하위 데이터 보존·복구를 검증한다.
- dependency, native, schema, sync 계약을 바꾸거나 큰 기능 묶음을 종료할 때만 전체 `npm run verify`를 실행한다.
- 작은 UI 수정마다 APK, 원격 DB, 전체 실기기 시나리오를 반복하지 않는다.
- 실기기 확인은 변경된 핵심 흐름을 한 번 확인하고 build/OS/기기와 실제 결과만 기록한다.
- 대규모 시각 변경은 Mobbin 역할표 → high-fidelity Figma → frame별 design context/screenshot → 읽기 전용 시각 검수 → 화면 단위 구현 → 합성 데이터 기기 비교 순서로 진행한다. Figma 승인 전에는 코드·APK 검증을 반복하지 않는다.
- screenshot 자동 비교는 환경·폰트·테마를 고정한 합성 데이터 테스트의 drift 탐지 보조수단이다. 개인용 실기기 데이터를 초기화하지 않으며 수치 일치만으로 UX·접근성 승인을 대체하지 않는다.
- 데이터 손실 가능성, 승인하지 않은 과금·공개, 불변조건 충돌이 생기면 해당 범위만 멈추고 사용자에게 구체적으로 보고한다.

- Phase 1, 2, 4, 4R, 4S, 5의 완료 증빙을 보존한다.

## 10. 현재 비범위

- 결제·구독·광고, 공개 스토어 배포, 공개 계정 서비스
